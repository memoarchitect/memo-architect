Title

Say the name once: meMO, pronounced me-mo. The title is the story. Start with architecture modeling as code, then explain how the ontology makes safety assurance computable. meMO is a concrete open reference direction, not a product claim.

02 The opening problem
Medical-device safety assurance is increasingly a systems problem

Medical devices are becoming more complex. The safety question is getting harder.

Software now carries more product behavior. Connected services and post-market updates add dependencies. AI-enabled functions introduce model, data, monitoring, and fallback concerns. Regulatory expectations continue to evolve alongside the technology.

How do we know the system is still safe?
Concrete example | connected device after release

A connected therapy device needs a cybersecurity patch.

FDA section 524B: sponsors of cyber devices must plan for post-market vulnerabilities and make updates and patches available for the device and related systems.
01Which interfaces, modes, and dependencies can the patch affect?
02Which hazards and risk controls must be reviewed?
03What verification evidence belongs to the patched release?
The code diff may be small. The safety argument is a system question.
Source: FDA, Cybersecurity in Medical Devices FAQs, section 524B; FDA cybersecurity guidance, February 2026.

The opening problem

Open with the public-health question, then ground it in the connected-device patch example. FDA section 524B requires cyber-device sponsors to plan for vulnerabilities and make post-market updates and patches available. The architecture questions are an engineering inference: what behavior, risk controls, and verification evidence must be reviewed for the patched release? AI-enabled functions add a related change-management challenge; FDA also notes that the traditional device-regulation paradigm was not designed for adaptive AI/ML technologies.

03 Problem 01 | Complexity moved upward

Software complexity has outgrown component-by-component assurance.

Medical devices are software-defined cyber-physical systems

Safety-relevant behavior now crosses layers, interfaces, and released configurations.

Therapy logic interacts with sensing, hardware, connectivity, clinical workflow, faults, configuration, and updates. AI-enabled functions add model, data, monitoring, and fallback concerns.

Still necessary Is each component implemented correctly?
Now also required Can we explain the behavior of the system as a whole?

Complexity moved upward

Start with the direct argument. Software complexity has moved the safety question above individual components. Do not claim that every AI component is nondeterministic. The concrete point is that AI-enabled functions add model, data, monitoring, and fallback dependencies that must stay visible in the architecture.

04 Why the problem matters now

One safety question. Different pressure across the ecosystem.

Regulators, established manufacturers, and startups are not solving the same operational problem. They converge on the same need: a defensible system argument that survives change.

Perspective 01Regulators and reviewers

Can the released baseline be defended?

Reviewers need an end-to-end thread: hazard, control, where the control acts in the architecture and behavior, verification evidence, and the exact released configuration.

Need: objective evidence and an explainable change-impact scope.
Perspective 02Established manufacturers

Can meaning survive scale and time?

Many owners update risk, requirements, architecture, software, cybersecurity, tests, and release artifacts across long-lived products and fragmented toolchains.

Need: keep safety assumptions aligned through handoffs and post-market change.
Perspective 03Startups and small teams

Can rigor grow without process debt?

A small team carries therapy design, architecture, implementation, risk controls, and evidence. Structure is often deferred until submission pressure makes rework expensive.

Need: an incremental method that starts small and remains inspectable.
Shared requirementArchitecture-backed evidence that remains explicit, reviewable, and refreshable under change.

Ecosystem pressure

Use the proposal's audit and review expectation carefully. Regulators and reviewers want a defensible released baseline. Established manufacturers struggle with semantic fragmentation across scale and time. Resource-constrained teams struggle to add structure early enough. Do not caricature any group; the shared need is architecture-backed evidence under change.

05 Problem 02 | Partial knowledge

Safety decisions are made across disciplines, with partial knowledge.

Risk analysis, failure-mode analysis, and change-impact analysis require different experts to reason about one system without requiring everyone to hold every implementation detail.

Perspective 01Clinical + risk

What can harm the patient?

Clinical sequence, use conditions, foreseeable misuse, severity, and risk controls.

Perspective 02Systems + architecture

Where is behavior allocated?

Responsibilities, boundaries, interfaces, modes, flows, and constraints.

Perspective 03Software + hardware

What actually changed?

Implementation detail, dependencies, failure behavior, configuration, and tests.

The gap: the decision depends on all three perspectives, but the supporting knowledge is fragmented across people and artifacts.
Shared analytical layer

System and software architecture

A reviewable model gives each discipline a common place to connect what it knows and challenge what it assumes.

Cross-functional reasoning

This is not a complaint about expertise. It is the normal shape of medical-device development. Clinical, risk, systems, software, and hardware expertise remain distinct. Architecture is the shared analytical layer where those partial perspectives become an inspectable system argument.

Problem 04 | static artifacts

Trace links prove connection. They do not explain behavior.

The missing capability: a reviewable model that can answer impact questions across structure, behavior, risk controls, verification, and the released baseline.

Document-centric limits

Documents remain part of the regulated lifecycle. meMO is not a document replacement pitch. The issue is using documents and traces as the only analytical substrate for a complex system.

08 Problem 05 | Generic methods leave adoption work

Generic modeling languages exist. Adoption is still hard.

SysML and MBSE provide powerful foundations. A medical-device team still has to decide how to organize the model for its own safety, quality, and product context.

Language

What should we model?

Layers, element types, relationships, and the minimum detail that supports a decision.

Method

How should the team work?

Viewpoints, views, review gates, ownership, workflow, and evidence closure.

Adoption

How much process is enough?

A heavyweight transformation can stall. An underspecified approach leaves every team inventing conventions.

meMO aims to provide a lightweight, medical-device-oriented starting point so teams can focus on the product and extend only what their context needs.

Generic MBSE is not enough

Do not position meMO against SysML. meMO builds on the idea of model-based engineering and supplies a medical-device-oriented organization, semantic vocabulary, and lightweight method.

09 The bridge

The missing layer is architecture.

Medical-device teams often have deep implementation detail and extensive traceability. What is missing is a reviewable model of how the system behaves as a system.

One end

Code-first detail

Source code, unit tests, tickets, and low-level designs are necessary. They do not expose the whole safety argument.

  • A component can pass tests while an interface assumption fails.
  • A thread optimization can alter timing behavior.
  • A configuration change can affect a clinical mode.
The analytical middle

System and software architecture

This is where teams reason about allocation, interaction, modes, contracts, and emergent behavior before the evidence package drifts away from reality.

Where is the safety control realized? When does it act? What changes when this component changes?
Other end

Traceability without analysis

Links and documents can accumulate while their semantics remain too weak to explain system behavior.

  • A hazard links to a requirement, but not to a component.
  • A control exists on paper, but not in a scenario.
  • A test exists, but its released baseline is unclear.

Architecture gap

This is the code-first audience bridge. The argument is not that teams need more diagrams. They need the level of abstraction where structure and behavior can be analyzed together. Architecture sits between code detail and compliance trace.

10 Second-level effects

Under change, the gap becomes evidence decay.

Safety claims, architectural intent, behavioral scenarios, risk controls, and verification evidence gradually lose alignment as the product evolves.

Underlying systems problem

Evidence integrity is hard to preserve under change.

The failure is not one broken hyperlink. It is the loss of a defensible explanation of what the device does and why the released baseline remains safe.

Result: over-verify or under-verify.

Weak foundations

Ambiguous intended use and operational assumptions. Tool and stakeholder fragmentation across the V-model.

Architecture blind spots

Controls not allocated to components or interfaces. Architecture coupling, emergent behavior, and implicit interface contracts.

Behavior blind spots

Edge cases remain prose. Modes, degraded paths, misuse cases, and scenario coverage are not first-class.

Evidence blind spots

Artifact granularity does not match. Risk, architecture, requirements, tests, and released evidence become stale.

Release decision

Change impact is reconstructed manually. Teams either retest too much because the blast radius is unclear, or retest too little because a dependency was missed.

Evidence decay under change

This slide lays out the full problem set from the white paper. Do not linger on every item. Show that the issues are connected: weak assumptions, architecture blind spots, behavior blind spots, evidence drift, and then an undefendable release scope.

11 Introduce meMO at the concept level

meMO is a modular starting point, not a prescribed transformation.

Teams can adopt the language, the lightweight method, and the reference runtime together or selectively. The center of gravity is an inspectable architecture model.

01 | LANGUAGE

meMO Ontology

A medical-device-oriented vocabulary of typed architecture, behavior, risk, assurance, artifact, and viewpoint concepts with semantic relationships and closure rules.

02 | PLAYBOOK

meMO Method

A lightweight, tailorable way to move from context to architecture, scenarios, risk overlays, verification, and evidence without prescribing one organizational process.

03 | RUNTIME

meMO Architect

An optional reference implementation: text-first modeling, validation, impact analysis, compiled views, and review workbenches over the same versioned model.

Optional starter contentWorked examples, patterns, and profiles provide a place to begin. Teams keep their product-specific decisions and existing lifecycle systems.

meMO modular split

Introduce meMO without implementation details. The audience should first understand the separation: a semantic language, a lightweight playbook, and an optional runtime. A team can implement the pattern with its own tooling.

16 Lightweight method

Use a light architecture method, then tailor it.

meMO is inspired by architecture-centric methods such as Arcadia: begin with need and behavior, separate logical responsibilities from realization, and add risk and evidence as first-class overlays.

01Operational contextClinical setting, actors, intended use, system boundary
02Functions + flowsWhat transformations and interactions must occur?
03Logical architectureResponsibilities, boundaries, interfaces, contracts
04RealizationSoftware, hardware, physical interfaces, configuration
05Behavior scenariosModes, faults, edge cases, degraded paths
06Assurance overlaysRisk, cybersecurity, verification, evidence closure

Non-prescriptive

Select the depth needed for a decision. Do not model for ceremony.

Customizable

Profiles choose concepts, aliases, rules, gates, views, and artifact bindings.

Incremental

Start with one safety thread and expand as the product and team need it.

Lightweight method

This addresses the gap left by generic modeling languages. The method is inspired by architecture-centric approaches, but it is deliberately lighter and tailorable for medical-device teams. It is not a replacement for an organization's QMS.

20 Use the pattern without buying the promise

Start with one architecture-backed safety thread.

meMO is a reference direction. The transferable method can be piloted with the modeling stack your team can sustain.

Designed to help teams

  • make controls concrete in components, interfaces, and behavior steps
  • represent modes, scenarios, contracts, and edge cases explicitly
  • surface incomplete safety threads through closure constraints
  • derive change-impact candidates for expert review
  • compile repeatable views from a versioned baseline

Does not claim to

  • certify a device or decide safety acceptability
  • prove code correctness from a complete graph
  • replace QMS, ALM, or specialized analysis tools
  • provide 21 CFR Part 11 compliance or tool qualification today
  • remove engineering judgment

A practical pilot

  • one hazard
  • one control
  • one architecture allocation
  • one behavior scenario
  • one verification case
  • one closure check
  • one real change

Scope and pilot

Land the boundary clearly. The method is useful before a platform rollout. Pick one clinically meaningful thread and compare the quality of review before and after the model-assisted analysis. Expand only if the pilot improves a real workflow.
