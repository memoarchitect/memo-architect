02 The starting point

Medical-device safety assurance is an architecture problem.

Modern devices combine software, hardware, users, operating modes, configuration, and increasingly connected services. Safety depends on their interactions.

Safety is not a property of an isolated requirement or code unit.

A component may pass its unit tests while an interface assumption, timing interaction, alarm path, or mode transition still creates a hazardous condition.

The engineering problem: connect system architecture, software architecture, and behavior to the safety argument at the same level of precision as the design evolves.

Start with the underlying problem from the white paper. A medical device is a cyber-physical system. Safety emerges from architecture and behavior, including modes and off-nominal conditions. This is why disconnected document review becomes fragile.

03 The missing middle

Teams often skip the layer needed for system reasoning.

Low-level implementation detail and exhaustive traceability are both useful. Neither explains how a medical device behaves as a system.

One end

Code-first detail

Teams can inspect source, unit tests, tickets, and low-level designs while still lacking a reviewable model of the system.

  • Which component owns the safety control?
  • Which interface assumptions matter?
  • Which mode transition changes behavior?
Missing middle

System and software architecture

Architecture provides the level where teams can reason about allocation, interaction, behavior, and change impact without drowning in code or stopping at hyperlinks.

components + interfaces
modes + scenarios
controls + behavior guarantees
verification obligations
Other end

Traceability without analysis

Teams can accumulate requirement links and evidence references while the meaning of those links remains too weak for system analysis.

  • Where is a control realized?
  • When does it act?
  • What must be re-reviewed after change?

1:30 - 2:25 | Architecture gap

This is the key argument for code-first and non-MBSE teams. Architecture is not a request for more diagrams or process. It is the missing level of abstraction for analyzing components, interfaces, modes, scenarios, and safety-control realization under change.

04 Change makes the gap operational

After a change, teams face two bad options.

The release question is not simply whether a diff exists. It is whether the proposed re-review and re-verification scope is sufficient.

Option A

Over-verify

Retest too much because the blast radius is unclear. Cost rises, schedules slip, and scarce V&V capacity is consumed by work that may not be safety relevant.

Option B

Under-verify

Retest too little because a dependency was missed. A changed interface assumption, mode transition, or control realization can escape review.

The practical target: a defensible, reviewable explanation of what changed, what it impacts, and why the proposed scope is enough.

2:25 - 3:15 | Release decision

This is the operational consequence. Do not use recall statistics or invented cost percentages. The white paper supports the precise claim: manual impact assessment pushes teams toward excessive retest or missed safety impacts.

05 Same problem, different constraints

Scale and scarcity expose the same evidence-integrity gap.

The failure mode is shared. The operating constraints differ.

Established manufacturer

Many owners. Long-lived baselines.

Cross-functional handoffs: requirements, architecture, risk, cybersecurity, V&V, and quality evidence are maintained by different teams.

Post-market evolution: changes must be assessed against prior assumptions and released evidence.

Problem: integrated review becomes expensive when semantics are distributed.

Resource-constrained team

Fast learning. Limited infrastructure.

Parallel responsibilities: a small team is developing the therapy, architecture, software, risk controls, and evidence package at once.

Late formalization: safety knowledge can accumulate in spreadsheets, tickets, and documents.

Problem: late restructuring creates avoidable rework when runway is limited.

Shared need: an incremental method to preserve evidence integrity as complexity and organizational scale grow.

3:15 - 4:05 | Organizations

Keep this grounded. Avoid claiming every startup or large company operates the same way. The white paper supports the distinction: fragmentation at scale and accessibility for resource-constrained organizations.

06 What reviewers actually need

For an important hazard, show one complete thread.

A defensible review needs more than a trace matrix. It needs the control, where it is realized, when it acts, how it is verified, and which released baseline the evidence supports.

1

Hazard

What patient or system risk are we addressing?

2

Risk control

What reduces the risk?

3

Allocation

Where is the control implemented?

4

Scenario

In which mode, flow, alarm path, or edge case does it act?

5

Verification

What test or analysis demonstrates the control?

6

Baseline

Which released configuration does the evidence support?

Architecture is the analytical bridge. A hyperlink alone does not explain where a control is realized, when it acts, or whether the safety thread is complete.

4:05 - 5:00 | Review thread

This is the audit-and-review expectation from the white paper. It sets up the ontology naturally. A reviewer wants one coherent safety thread tied to the exact released baseline.

07 Minimal mechanism

Make architecture explicit, typed, and checkable.

The core proposal is small: represent system and software architecture, behavior, and assurance obligations using a medically grounded vocabulary, then evaluate closure conditions over that model.

5:00 - 6:00 | Ontology

This is the center of the talk. Avoid saying the ontology automates compliance. It provides typed semantics and checkable closure conditions. The current repository is migrating those rules to native SysML v2 constraints evaluated by a KerML subset.

Keep the model small. Expand only after the first thread improves a real review workflow.

7:10 - 8:10 | Pilot recipe

This is the practical takeaway. Do not prescribe a full platform or language migration. A team can pilot the method with SysML v2, a graph database, JSON, or another typed representation. The meaningful milestone is one improved review workflow.

10 Memo: reference implementation direction
