meMO: Medical Device Architecture Modeling as Code for Ontology-Backed Safety Assurance

Ontology-driven architecture and behavior models that turn trace links into computable assurance evidence.

Somesh Kashyap | Medtronic

Title

Say the name as me-mo. The talk is about a direction people can implement independently: model architecture and behavior as code, attach safety meaning through a small ontology, and compute useful evidence checks. Avoid presenting meMO as an automatic safety tool.

03 Problem 01 | emergent behavior

A component can be correct while the system is unsafe.

Many safety-relevant failures emerge between components, modes, and clinical actions.

Safety is a system property: structure, interfaces, modes, timing, and scenarios must be analyzed together.

Safety emerges across interactions

This is an illustrative interaction chain, not a claim about a specific device. The point is that unit correctness is necessary but not sufficient. Safety analysis needs architecture and dynamic scenarios to explain composition.

17 Clear boundaries

What meMO solves, and what it deliberately does not.

Helps teams do

  • Make architecture responsibilities and interfaces explicit
  • Connect risk controls to behavior and verification evidence
  • Detect incomplete threads and surface change-review scope
  • Compile consistent views from a versioned model

Does not claim to

  • Certify compliance or decide safety acceptability
  • Replace expert judgment, a QMS, or specialized analysis tools
  • Require a proprietary modeling repository
  • Deliver every enterprise integration today

Clear boundaries

This slide is essential for credibility. meMO organizes and checks evidence semantics. It does not automate the safety decision, replace the QMS, claim tool qualification, or pretend that all integrations exist today.

18 A practical starting point

Do not start with a platform rollout. Start with one safety thread.

The method is useful when the smallest pilot already improves a real engineering review.

01Choose a hazardPick one meaningful control and its clinical context.
02Model the architectureName the responsible component, interface, and scenario.
03Link the evidenceAdd verification intent and acceptance criteria.
04Review a changeUse the model to scope what must be reconsidered.
Success criterion: the next design review asks a better system-level question.

Start with one thread

This is implementable independently. Choose one safety-relevant thread, represent its architecture and scenario, link the control and verification intent, and then use a real change to test whether the model improves the review discussion.
