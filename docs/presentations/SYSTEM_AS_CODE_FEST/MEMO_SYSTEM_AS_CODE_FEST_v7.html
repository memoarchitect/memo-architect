03 Problem 01 | emergent behavior

A component can be correct while the system is unsafe.

The code can run. The architecture can still contain a contradiction.

Example 01 | competing control paths

Two valid corrections. One unsafe total dose.

An automated controller and a clinician can both request a therapy correction.

The controller schedules an automatic correction.
A clinician requests a manual correction.
Each command is valid when checked alone.
Both reach the actuator. Possible patient harm: overdose.
Architecture check: every delivery command must pass one cumulative-dose arbitration rule.
Example 02 | interface contract drift

The field still parses. Its meaning changed.

A sensor service changes its pressure output from mmHg to kPa.

The interface still sends a numeric value.
The alarm service still receives the value.
Its threshold still assumes mmHg.
The threshold is wrong. Possible patient harm: dangerous pressure is missed.
Architecture check: a unit change must invalidate downstream assumptions.
Example 03 | timing budget regression

Each component works. The response is late.

A signal-processing update improves accuracy but increases compute time from 80 ms to 180 ms.

The sensor still produces valid samples.
The algorithm still returns the right result.
The control loop still runs.
Response exceeds 250 ms. Possible patient harm: therapy adjustment arrives late.
Architecture check: a component latency increase must fail the allocated response-time budget.
The engineering goal: make violated system contracts fail review early, like compile errors for architecture.

Safety emerges across interactions

These are illustrative engineering scenarios, not claims about a specific device. The first shows a composition failure: two locally valid delivery commands become unsafe without system-level arbitration and a cumulative-dose constraint. The second shows why syntax-level compatibility is insufficient: a value can still parse while its semantics have changed. The third shows a timing-budget regression: local correctness does not guarantee an acceptable end-to-end response. Each technical inconsistency can propagate to patient harm. meMO does not prove safety automatically. The ontology, methodology, and tooling make modeled contracts, assumptions, and missing consistency visible and checkable earlier.

Existing solutions

Start with respect for existing practice. ISO 14971 frames risk management across the medical-device life cycle. IEC 62304 defines software life-cycle processes. FDA guidance expects software validation, cybersecurity architecture and SBOM information, interoperability risk analysis, and risk-based evaluation of software modifications. Teams therefore already create many necessary artifacts. The problem is the handoff: after a code change, can the team compute the affected system behavior, controls, verification scope, and evidence freshness?

The matrix describes repository ownership boundaries, not product deficiencies. QMS and ALM platforms are authoritative for controlled work products, approvals, and trace records. MBSE environments are authoritative for architecture semantics when teams adopt them. Git and CI are authoritative for implementation diffs and automated outcomes. Each assurance decision depends on information owned in the other repositories. Integrations can move data, but the cross-layer semantics and impact paths still need an explicit model.

Keep this slide simple during the talk. The audience should leave with three practical costs: adding tools and methods is expensive; safety knowledge remains fragmented across disciplines and repositories; and engineers repeatedly reconstruct cross-layer impact paths during review. Where the gaps remain

Now name both parts of the problem. The architecture boundaries are real: controlled records, system models, and implementation repositories own different parts of the safety argument. The adoption barriers are also real: tool and integration costs, time to establish profiles and viewpoints, methodology variation across organizations and product lines, and the ongoing effort required to keep models synchronized with engineering change. Avoid implying that MBSE or ALM tools cannot solve these problems when configured well. The point is that many teams cannot afford to assemble and sustain a heavyweight solution before product work can benefit.

08 What ontology means

An ontology is an explicit domain model, not a vocabulary list.

It defines the kinds of things that may exist, the semantics of their relationships, and invariants that must hold.

Working definition for this talk

A versioned, tool-independent semantic contract for medical-device architecture.

The ontology makes model statements interpretable by both reviewers and software. In meMO, it is expressed as portable SysML v2 content rather than hidden inside a proprietary database.

23 Clear boundaries

What meMO helps with, and what it deliberately does not.

Helps teams do

  • Make architecture responsibilities and interfaces explicit
  • Connect risk controls to behavior and verification evidence
  • Detect incomplete threads and surface change-review scope
  • Compile consistent views from a versioned model

Does not claim to

  • Certify compliance or decide safety acceptability
  • Replace expert judgment, a QMS, or specialized analysis tools
  • Require a proprietary modeling repository
  • Deliver every enterprise integration today
Direction, not magic: meMO structures assurance work without replacing engineering judgment.

Clear boundaries

Maintain credibility. meMO structures meaning, checks consistency, and supports review. It does not certify compliance, replace the QMS, replace specialized safety analyses, or claim all roadmap capabilities are complete.
