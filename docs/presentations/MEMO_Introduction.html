Part Two

Why is it still hard?

Other industries already lean on architecture. Medical doesn't — and the reasons differ for enterprises and startups. Both hit the same tooling wall.

02

Aerospace and automotive are more mature.

They have strong traditions of architecture, allocation, interface contracts, and model-based reasoning. Medical has strong process — but low architecture and MBSE adoption.

06 The adoption bottleneck

Startups and enterprises struggle differently.

Different strengths, the same wall: tooling cost and method-setup effort block adoption — even inside large organizations.

Enterprise

Mature, but slow

Formal evidence and review culture — fragmented across tools.

  • Tool silos and handoffs
  • Slow, manual change impact
  • Document drift between baselines
Startup

Fast, but thin

Code-first iteration and direct ownership — weak on process.

  • Immature risk analysis
  • Implicit, undocumented architecture
  • Limited tooling budget
Common blocker

Tooling cost

MBSE / QMS / ALM suites are expensive — even big orgs feel it.

  • Organizing viewpoints = a lot of work
  • Method setup before any value
  • Versioning & diffing still painful
Enterprises need speed and integration. Startups need safety discipline — neither can afford an enterprise tool-and-method tax to get it.

09 Layer 01 · Ontology

meMO Ontology — typed medical meaning.

A minimal, medically grounded vocabulary so evidence relationships carry typed meaning — published as an open SysML v2 spec, one memo:: namespace, version 1.0.0.

What it defines
  • Typed elements — Intended Use, Hazards & Harms, Risk Controls, Requirements, Architecture, Behavior, Verification.
  • Typed relationships — semantic links with roles, not free-form arrows.
  • Closure constraints — completeness rules (CR-MED-*) traced to ISO 14971 / IEC 62304.
  • 18 architecture layers — risk and cybersecurity modeled as peers.
HazardRiskControlRequirementVerificationCaseEvidenceSemanticLink
Why it matters
  • Evidence relationships become checkable, not just visible.
  • Stable identifiers + controlled vocabulary across tools and teams.
  • Tool-agnostic and open — reduces lock-in, enables independent review.
  • Aligned to ISO/IEC/IEEE 42010 (viewpoints) and Arcadia-style layering.
The ontology is the source of truth — everything else projects from it.
A safety thread becomes a typed object — hazard → control → allocation → verification → evidence — that rules can check.
10 Layer 02 · Methodology

meMO Methodology — a ramp onto the ontology.

Instead of asking every team to invent a medical-device MBSE method, meMO ships a prefab practice: pick rigor, pick viewpoints, author rules, bind to a project.

Rigor profiles

Lightweight · balanced · formal — MethodRigorKind sets how much the method demands.

Viewpoints (ISO 42010)

Default viewpoints per audience and workflow stage; views bind intent to content.

Rules & gates

ViewRule (required / recommended / forbidden), workflow stages, and ReviewGate exit criteria.

Project binding

ProjectMethodBinding pins a resolved method to a project — patterns included.

Methodology is the ramp. It reduces the blank-canvas problem and the cost of adopting architecture-centered assurance.

16 memo::core

A small core: bases, enums, links.

The whole ontology specializes a handful of abstract bases. Enumerations encode categorical attributes; links carry typed semantics.

core/memo_common.sysml
part def IdentifiedElement {
  attribute id : String;
  attribute name : String;
  attribute description : String;
}
part def TraceableElement :> IdentifiedElement {
  attribute rationale : String;
  attribute sourceReference : String;
}
part def ArchitectureElement :> TraceableElement;
part def VerifiableElement   :> TraceableElement;
part def EvidenceElement     :> TraceableElement;
57 enumerations

ConcernKind · SafetyClassKind · HazardTypeKind · RiskControlKind · ThreatCategoryKind · AudienceKind …

Semantic links

SemanticLink → RequirementSatisfactionLink, VerificationLink, FunctionAllocationLink …

Specialize, don't edit

Every domain element :> specializes a base. Add kinds; never fork the core.

Categorical meaning is enumerated, structural meaning is typed. That is what makes the model checkable.
17 Risk & security

Safety and security as peer layers.

A hazard chain on one side, a threat chain on the other — both feed the same RequirementDriver / VerifiableElement contract.

architecture/memo_risk.sysml
part def Hazard :> TraceableElement {
  attribute hazardType : HazardTypeKind;
  attribute foreseeable : Boolean;
}
part def RiskControl :> VerifiableElement {
  attribute controlKind : RiskControlKind;
}
part def RiskAfterMitigation :> Risk {
  attribute residualAcceptability : String;
}
architecture/memo_cybersecurity.sysml
part def CybersecurityAsset :> ArchitectureElement {
  attribute assetKind : AssetKind;
  attribute safetyRelevant : Boolean;
}
part def Threat :> RequirementDriver {
  attribute threatCategory : ThreatCategoryKind;
  attribute attackVector : String;
}
// Threat :> RequirementDriver — exactly like Risk.
Why peers: because Threat drives requirements just like Risk, the same downstream machinery generates security requirements and verification.
18 Semantic links

Links carry roles — not just direction.

Every link is a SemanticLink subtype with named part roles and a link status. The linker checks the element kind on each end.

Traceability is data, not a matrix. The RMF view, V&V matrix, and impact analysis all read the same SemanticLink instances.

20 Worked example

Meet GPCA — memo::examples::gpca

A Generic Patient-Controlled Analgesia infusion pump — the public-domain U. Minnesota CriSys benchmark, IEC 62304 Class C.

Why GPCA
  • U. Minnesota CriSys benchmark, public REQ catalogue (REQ 1–86).
  • IEC 62304 Class C software with a full ISO 14971 hazard chain.
  • Cited across FDA, NIH, and INCOSE literature.
  • Real instances in the repo — not pseudo-code.
What is modeled
  • Stakeholders, intended use, needs & software requirements.
  • Hierarchical mode machine — OFF · IDLE · PAUSED · BASAL · SQUARE · PBOLUS.
  • SW components (Top_Level_Mode, Alarm, Infusion_Manager …) with period / deadline / WCET.
  • Hazard chain + lockout control; STRIDE threat model; AGREE-like & LTL properties.
One model, every layer: requirements, architecture, interfaces, behavior, risk, cyber, verification, trace, and document views.

22 Compile the argument

We compile code. We should compile the safety argument.

Architecture review questions become executable checks. meMO ships native KerML closure constraints traced to ISO 14971, IEC 62304, and ISO 13485.

terminal — closure & consistency
$ memo validate

CR-MED-001  Hazard must have ≥1 risk control   (ISO 14971)
            Missing mitigation: hazAirInLine

CR-MED-003  Risk control must be verified      (ISO 14971 §7.4)
            Missing verification: rcDoorOpenAlarm

CR-MED-011  SW requirement must derive from a
            system requirement                (IEC 62304)

Result: 2 errors · 1 warning · safety thread HZ-001 closed
Why it matters
  • Find gaps before design review or audit.
  • Make closure visible to software, systems, risk, and V&V at once.
  • Run the rules in CI before merge or release.
  • Turn each change into a deterministic re-review scope.
The memorable hook: safety evidence becomes something engineers can validate, like a build.
