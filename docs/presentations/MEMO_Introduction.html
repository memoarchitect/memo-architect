Safety evidence drifts under change.

Medical devices became software-intensive systems. Their safety case is spread across documents that are traced but not always meaningful — and it loses alignment as the design evolves.

04 The gap

What medical devices still lack.

Medical has mature standards (ISO 14971, IEC 62304) and process — but not the architecture-centered semantic backbone the other domains rely on.

Documents, not a model

Architecture lives as block diagrams that age — not a queryable, versioned model.

Low MBSE adoption

Heavyweight tools and months of setup keep model-based methods out of reach.

No shared semantics

Risk, design, and V&V don't share typed meaning — links are free-form and unchecked.

Manual change impact

Re-verification scope is guessed by hand, so evidence drifts between releases.

Medical has the standards and the process — what it lacks is a low-cost, architecture-centered model that ties them together.

Methodology — predefined practice.

So teams start from a working structure rather than an empty model: pick a rigor level, use default viewpoints, apply rules, and bind the method to a project.

Rigor profiles

MethodRigorKind — lightweight, balanced, or formal — sets how much the method requires.

Viewpoints (ISO 42010)

Default viewpoints per audience and workflow stage; views bind that intent to content.

Rules & gates

ViewRule (required / recommended / forbidden), workflow stages, and ReviewGate exit criteria.

Project binding

ProjectMethodBinding pins a resolved method, with reusable modeling patterns.

The methodology is editable and extendable — it guides how the ontology is applied without changing the ontology.

Tools — a compiler for compliance.

A Turbo monorepo: a Langium-based core engine and a Commander CLI parse text-first models into a semantic graph and run the rules.

$ cd examples/gpca-pump && memo dev
  → live model + validation at localhost
What the tools do
  • Parse text-first SysML v2 into a semantic graph.
  • Run native KerML closure & consistency checks — errors, warnings, completeness.
  • Import / export: Enterprise Architect, Cameo, OWL, CSV.
  • Generate DHF artifacts; validate in CI before review or release.
Compliance becomes compiler-like: run memo validate in CI and turn each change into a deterministic re-review scope.

Requirements — needs become typed obligations.

Definitions on the left; the same kinds instantiated in GPCA on the right. Requirements are SysML v2 requirement defs, not docstring fields.

architecture/memo_requirements.sysml — definitions
requirement def StakeholderNeed :> RequirementDriver;
requirement def Requirement :> VerifiableElement {
  attribute statement       : String;
  attribute sourceKind      : RequirementSourceKind;
  attribute acceptanceCriteria : String;
}
requirement def SoftwareRequirement :> Requirement {
  attribute safetyClass : SafetyClassKind;
}
examples/gpca — instances
requirement needSafeTherapy : StakeholderNeed {
  attribute id = "NEED-001";
  attribute statement =
    "Support safe patient-controlled therapy.";
}
requirement reqLockout : SoftwareRequirement {
  attribute id = "REQ-025";
  attribute sourceKind = RequirementSourceKind::risk;
  attribute safetyClass = SafetyClassKind::C;
}
Same kinds, real values. REQ-025 carries its source (risk) and safety class as typed attributes — queryable, not prose.

Risk — hazard, control, residual.

The ISO 14971 chain as typed parts. Cybersecurity is a peer layer: Threat :> RequirementDriver, driving the same machinery as risk.

architecture/memo_risk.sysml — definitions
part def Hazard :> TraceableElement {
  attribute hazardType  : HazardTypeKind;
  attribute foreseeable : Boolean;
}
part def RiskControl :> VerifiableElement {
  attribute controlKind : RiskControlKind;
}
part def RiskAfterMitigation :> Risk {
  attribute residualAcceptability : String;
}
examples/gpca — instances
part overdoseHazard : Hazard {
  attribute id = "HZ-001";
  attribute hazardType = HazardTypeKind::drugDeliveryError;
  attribute severity   = CriticalityKind::catastrophic;
}
part lockoutControl : RiskControl {
  attribute id = "RC-001";
  attribute controlKind = RiskControlKind::inherentSafeDesign;
}
Safety and security are peers — both feed the same RequirementDriver / VerifiableElement contract downstream.

Assurance — cases, tests, evidence.

The verification layer closes the thread: a case with acceptance criteria, a test artifact, and evidence tied to a baseline.

architecture/memo_assurance.sysml — definitions
part def VerificationCase :> VerifiableElement {
  attribute methodKind        : VerificationMethodKind;
  attribute acceptanceCriteria : String;
}
part def TestArtifact :> EvidenceElement;
part def Evidence :> EvidenceElement {
  attribute evidenceType    : String;
  attribute integrityStatus : String;
}
examples/gpca — instances
part vcLockout : VerificationCase {
  attribute id = "VER-002";
  attribute methodKind = VerificationMethodKind::test;
  attribute acceptanceCriteria =
    "No bolus when lockout / max bolus active.";
}
part evidenceLockout : Evidence {
  attribute id = "EVD-001";
  attribute evidenceType = "verification evidence";
}
Acceptance criteria are a typed attribute — the rule engine can check that every high-severity control reaches an Evidence node.
17 Connecting the layers

Typed links connect the layers.

Layers don't connect by free-form arrows. Every link is a SemanticLink subtype with named roles and a status — the linker checks the element kind on each end.

DomainLink kinds
RequirementRequirementSourceLink · RequirementSatisfactionLink
FunctionFunctionAllocationLink — function ↔ allocated element
InterfaceInterfaceRealizationLink · TrustBoundaryCrossingLink
VerificationVerificationLink · EvidenceProductionLink · DocumentInclusionLink
RiskRiskTraceLink (initiates · leadsTo · canCause · resultsIn · aggregates)
CyberAssetThreatLink · ThreatVulnerabilityLink · CyberSafetyTraceLink
Traceability is data, not a matrix. The RMF view, V&V matrix, and impact analysis all read the same SemanticLink instances.
18 Compile the argument

We compile code. We should compile the safety argument.

With everything typed and linked, review questions become executable checks — native KerML closure constraints traced to ISO 14971, IEC 62304, and ISO 13485.

terminal — closure & consistency
$ memo validate

CR-MED-001  Hazard must have ≥1 risk control   (ISO 14971)
            Missing mitigation: hazAirInLine

CR-MED-003  Risk control must be verified      (ISO 14971 §7.4)
            Missing verification: rcDoorOpenAlarm

CR-MED-011  SW requirement must derive from a
            system requirement                (IEC 62304)

Result: 2 errors · 1 warning · thread HZ-001 closed
Why it matters
  • Find gaps before design review or audit.
  • Make closure visible to software, systems, risk, and V&V at once.
  • Run the rules in CI before merge or release.
  • Turn each change into a deterministic re-review scope.
Compliance becomes a build step: safety evidence becomes something engineers can validate.

20 Extension

Extend through methodology profiles.

Pick rigor, pick viewpoints, author rules, bind to a project, add your own domain kinds. The core ontology stays unchanged.

1
Pick rigor · MethodRigorKind = lightweight | balanced | formal
2
Pick viewpoints · audience = safetyEngineer · stage = risk
3
Author rules · ViewRule · elementTypeName = "Hazard" · strength = required
4
Bind to project · ProjectMethodBinding · projectName = "GPCA Pump"
5
Add domain kinds · part def InfusionMode :> ModeState { … } in your own package
The rule: add packages and methodology profiles — don't edit core.
